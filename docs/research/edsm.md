## 1. General conventions

- **Base URL:** `https://www.edsm.net/`. The host is fronted by Cloudflare. API paths have no `/en/` prefix; the `/en/` prefix is only for HTML pages.
- **Response format:** every API response is JSON with `Content-Type: application/json`.
  - Query APIs say "most queries work with GET but should also be compatible with POST".
  - Observed response headers include:
    - `access-control-allow-origin: *`
    - `access-control-allow-methods: GET, POST`
    - `x-powered-by: EDSM.NET APIv1`, `EDSM.NET API-STATUSv1` or `EDSM.NET API-JOURNALv1`
    - `Cache-Control: max-age=86400` on `api-v1` and `api-system-v1`
- **HTTP status is 200 even for application errors.**
  - The real result is in `msgnum` and `msg`. A verified example is `GET /api-journal-v1` without parameters, which returns HTTP 200 with `{"msgnum":201,"msg":"Missing commander name","events":[]}`.
  - Treat HTTP non-2xx as a transport or server failure, and retry with backoff.
- **Credentials:**
  - `commanderName` is the name *as registered on EDSM*. It can differ from the in-game name, which is why EDMC asks for a separate "Commander Name".
  - `apiKey` is generated by the user at https://www.edsm.net/en/settings/api.
  - **No application registration is needed.** EDSM identifies software only through `fromSoftware` and `fromSoftwareVersion`, and can blacklist a software/version (msgnum 205).
- **User-Agent:** EDMC sends `EDCD-EDMarketConnector-<version>` on all requests. EDSM has no documented requirement. Send a stable, identifying UA such as `EliteNexus/<semver> (+https://github.com/<you>/EliteNexus)`.
- **Timeouts:**
  - EDDI's code comments that a **30 s timeout for journal POSTs was recommended by Anthor**, the EDSM author.
  - EDMC uses 20 s.
  - Use 30 s for the journal POST and 10–20 s for queries.
- **Server load:** the snapshot pages carry a banner saying EDSM is "currently experiencing some heavy load". Expect slow responses and occasional 5xx, and degrade gracefully.
- **Live galaxy only:**
  - Since Update 14 (2022-11-29), EDSM accepts only Live (4.0+) game data. Legacy/Horizons 3.8 and console data are not supported.
  - EDMC decides "Live" as `semver(gameversion) >= 4.0.0` (`monitor.py`, `live_galaxy_base_version`).

## 2. Journal upload API

### 2.1 Endpoint

```
POST https://www.edsm.net/api-journal-v1
```

- **Body encoding:** the docs say parameters can be sent "as a raw body JSON or like a form/multipart". In the field:
  - EDMC sends `application/x-www-form-urlencoded` through `requests` `data=`.
  - EDDiscovery sends `application/x-www-form-urlencoded` and URI-escapes the long `message`.
  - EDDI sends `multipart/form-data` and gives the `message` part `Content-Type: application/json`.
- **Recommendation:** use `application/x-www-form-urlencoded` with UTF-8. It is the best-trodden path.
- The docs say GET requests "will not be followed for security reasons".

### 2.2 Parameters (all required)

| Param | Type | Notes |
|---|---|---|
| `commanderName` | string | EDSM account commander name. EDMC sends it UTF-8 encoded. |
| `apiKey` | string | The user's EDSM API key. |
| `fromSoftware` | string | Your app name, e.g. `Elite Nexus`. Used by EDSM to blacklist broken software (msgnum 204/205). |
| `fromSoftwareVersion` | string | Your app version, e.g. `0.1.0`. |
| `fromGameVersion` | string | **Mandatory since 2022-11-29.** Use the `gameversion` from the journal `Fileheader` (or `LoadGame`), e.g. `4.0.0.1904`. **Only Live is accepted.** Use the EDDN rules: `Fileheader` first; for CAPI `/journal`-sourced data with no `Fileheader`, use `LoadGame.gameversion`. For CAPI-sourced data generally, use `CAPI-Live-<endpoint>`. EDDiscovery sends `CAPI-journal` for synthesised CAPI journals. |
| `fromGameBuild` | string | The `build` value from `Fileheader`/`LoadGame`, e.g. `r312345/r0 `. Pass it through as-is, **including trailing whitespace** (EDDN rule). |
| `message` | JSON string | Either one journal event object or a **JSON array of events** (batch). Send events "without modification", plus the transient `_xxx` fields in §2.3. |

Rules for batches:

- **One `fromGameVersion`/`fromGameBuild` per POST.** The version is claimed for the whole batch, so never mix versions. EDMC discards pending events if the version or build changes between queueing and sending.
- **Never mix commanders** in one POST, because credentials are per POST.

### 2.3 Transient-state fields (add to every event)

The journal does not carry full game state on every event. EDSM documents six optional "transient state" keys that you add to each event object you send. The default for each is `NULL`.

| Key | Type | Value |
|---|---|---|
| `_systemAddress` | int64 or null | Current `SystemAddress` (id64). |
| `_systemName` | string or null | Current star system name. |
| `_systemCoordinates` | `[x,y,z]` floats or null | Current `StarPos`, in journal light-year floats. EDSM multiplies by 32 and rounds internally. |
| `_marketId` | int64 or null | `MarketID` of the station the commander is docked at. |
| `_stationName` | string or null | Name of that station. |
| `_shipId` | int or null | Current `ShipID`. |

How EDSM consumes these (from `EDSM-NET/Journal-Events/Event.php`):

- **System resolution, in this order:**
  1. The event's own `SystemAddress`.
  2. `_systemAddress`.
  3. `StarSystem` (and `StarPos`) for `Docked`, `Location` and `Scan` events.
  4. `_systemName` (and `_systemCoordinates`).
  5. Game state inferred from earlier events in the *same batch*.
- **Coordinates:** a `NaN` coordinate is ignored. Coordinates are used to disambiguate duplicate system names.
- **Station resolution, in this order:**
  1. The event's `MarketID`.
  2. `_marketId`.
  3. `StationName` for `Docked`/`Location`.
  4. `_stationName`.
  5. Batch state.
- **Ship:** `_shipId` is used when it is `>= 0`; otherwise batch state is used. A ShipID of `4294967295` is treated as "no ship".

The official doc includes a reference JavaScript `updateGameStatus(entry)` tracker. The equivalent logic to implement:

| Journal event | Effect on tracked state |
|---|---|
| `LoadGame` | Clear system address, name and coordinates, and station market ID and name. |
| `SetUserShipName`, `ShipyardSwap`, `Loadout` | `shipId = entry.ShipID`. |
| `ShipyardBuy` | `shipId = null`. |
| `Undocked` | Clear station market ID and name. |
| `Location`, `FSDJump`, `Docked` | If `StarSystem` changed, clear the coordinates. If `StarSystem` is not `ProvingGround`/`CQC`, set `systemAddress = SystemAddress` (when present), `systemName = StarSystem`, and `coordinates = StarPos` (when present). Otherwise clear the system fields. Then set `marketId = MarketID` and `stationName = StationName` when present. |
| `JoinACrew`, `QuitACrew` | If you joined *someone else's* crew, stop sending events. Otherwise resume. In both cases clear the system and station fields. |
| (every event) | Stamp all six `_xxx` keys onto the event before queueing it. |

You also need the following, not in the EDSM reference JS:

- `CarrierJump` behaves like `FSDJump` for system and coordinates, and like `Docked` for the station when `Docked: true`.
- `SupercruiseExit`, `ApproachBody` and `Embark`/`Disembark` carry `SystemAddress` but no coordinates.
- `StartUp` (EDMC-synthetic) carries a full location.

What other clients actually send:

- **EDMC:**
  - EDMC sends **only** `_systemName`, `_systemCoordinates`, `_stationName` and `_shipId`. It never sends `_systemAddress` or `_marketId`.
  - It skips everything while in multicrew, where `state['Role']` is set.
- **EDDiscovery:**
  - Sends `_systemName`, `_systemCoordinates`, `_systemAddress` (when known), `_stationName` (when docked), `_shipId`, and `_convertedNetlog: true` for netlog-derived FSDJumps without `FuelUsed`.
  - When docked it also sends **`_stationMarketId`**. That key is *not* read by EDSM's handler, which reads `_marketId`, so it is a bug in EDD. Do not copy it.
- **EDDI:** sends all six documented keys, with explicit `null` when unknown.
- **Elite Nexus recommendation:** send all six documented keys on every event, with `null` when unknown.

### 2.4 Event preparation done by EDMC before sending

These details matter for parity:

- **Companion-file substitution.** EDMC's journal monitor replaces the stub journal event with the companion JSON file's content before plugins see it:
  - `Cargo` with `Vessel=Ship` and no `Inventory` is replaced by `Cargo.json`.
  - `ShipLocker` is replaced by `ShipLocker.json`.
  - `Backpack` is replaced by `Backpack.json`. The EDSM plugin explicitly uses `state['BackpackJSON']` for `BackPack`.
  - `NavRoute` is replaced by `NavRoute.json`.
  - `FCMaterials` is replaced by `FCMaterials.json`.
  - `ModuleInfo` is replaced by `ModulesInfo.json`.

  Do the same so EDSM gets the full inventory.
- **Synthetic `Materials` on `LoadGame`.** EDMC emits `{"timestamp": <LoadGame ts>, "event": "Materials", "Raw": [{"Name","Count"}...], "Manufactured": [...], "Encoded": [...]}` built from its tracked state, with the transient fields. This is because the real `Materials` event precedes `LoadGame` and is otherwise missed.
- **Synthetic `StartUp`.** When EDMC starts while the game is already running, or detects a new journal without the game running, it synthesises:

  ```json
  {"timestamp":"…","event":"StartUp","StarSystem":…,"StarPos":[…],"SystemAddress":…,"Population":…,
   "Body":…,"BodyID":…,"BodyType":…,"Docked":true|false,"MarketID":…,"StationName":…,"StationType":…}
  ```

  - `Body`, `BodyID` and `BodyType` are included only when known.
  - `MarketID`, `StationName` and `StationType` are included only when docked.
  - EDSM's event list says `StartUp` is used to "return current system for ED Market Connector". `StartUp` is *not* on the discard list. Its per-event reply carries `systemId` and `systemCreated`, which is how EDMC shows the "known/new system" icon.

### 2.6 Batching, size limits and send cadence

- **No maximum batch size or rate limit is documented** for `api-journal-v1` **[UNVERIFIED]**.
- What the reference clients do:

  | Client | Batching and cadence |
  |---|---|
  | **EDMC** | Accumulates pending events and POSTs when `should_send()` is true. Rules below. |
  | **EDDiscovery** | Up to **200 events per POST**. Holds `Cargo`, `Loadout`, `Materials`, `LoadGame`, `Rank`, `Progress`, `ShipyardBuy`, `ShipyardNew`, `ShipyardSwap`, and `Location`-while-docked for up to 20 s waiting for more events. Never mixes commander, data source, game version or build in one batch. Waits ≥100 ms between POSTs. On failure retries 5× with a 30 s → 60 s → 120 s → 240 s → 480 s backoff. Refreshes the discard list ≤ every 120 min. |
  | **EDDI** | 10 s start-up delay. Sends when the queue has been quiet for 2 s, then waits ≥10 s before the next POST. 30 s timeout. 3 retries with doubling delay from 10 s. Drops events older than its last successful sync timestamp. |

- **EDMC `should_send()` rules:**
  1. Always flush on `ShutDown` or `Fileheader`.
  2. After `NavBeaconScan`, hold the batch until `NumBodies` `Scan` events have arrived, then flush.
  3. Otherwise flush if *any* pending entry is "urgent":
     - `Cargo` is urgent only if the session did not start docked.
     - `Docked` is always urgent.
     - During the new-game burst (after `LoadGame`/`Commander`/`NewCommander`/`Location`, until `StartUp`) everything is urgent.
     - Otherwise every event is urgent **except** `CommunityGoal`, `ModuleBuy`, `ModuleSell`, `ModuleSwap`, `ShipyardBuy`, `ShipyardNew` and `ShipyardSwap`. Those wait for the next urgent event.
  4. The pending list is discarded on a new `Fileheader` or on a game version/build change, and cleared after `ShutDown`, `Commander` or `Fileheader`.
  5. Each flush gets 3 transport attempts. After that, the error "Can't connect to EDSM" is shown and the events stay pending.
- **Recommendation for Elite Nexus:**
  - Batch for 5–10 s of quiet time or up to 100–200 events.
  - Flush immediately on location-changing events (`FSDJump`, `CarrierJump`, `Location`, `Docked`, `StartUp`) so the UI can show the "new system" flag.
  - Keep ≥10 s between POSTs when backlogged.
  - Never parallelise POSTs for one commander. Order matters, because EDSM reconstructs state across the batch.
- **Duplicates:** EDSM caches each event for about 300 s (msgnum **103**) and dedupes already-stored events (**101**). Re-sending the same events after a crash is safe.

### 2.7 Response format

```json
{
  "msgnum": 100,
  "msg": "OK",
  "events": [
    { "msgnum": 100, "msg": "OK", "systemId": 27, "systemCreated": false, "shipId": 5 },
    { "msgnum": 304, "msg": "Discarded event" }
  ]
}
```

- **Top-level** `msgnum`/`msg` give the request status.
- **`events[i]`** is the result for the i-th submitted event, in the same order. EDMC and EDD both `zip()` request events with `events`.
- **Per-event extras** (from EDSM handler code `Event/FSDJump.php` and `Event/StartUp.php`):
  - `FSDJump` returns `systemId` (EDSM internal ID), `systemCreated` (bool, true when EDSM created the system, i.e. "new to EDSM") and `shipId`.
  - `StartUp` returns `systemId` and `systemCreated`.
  - Other handlers return just `msgnum`/`msg` **[UNVERIFIED for every handler]**.
- On a top-level 2xx error, `events` may be `[]`. This was verified for 201.

**msgnum codes** (official list; the descriptions are paraphrased):

| Code | Label (literal `msg`) | Meaning and handling |
|---|---|---|
| 100 | `OK` | Success. |
| 101 | `Message already stored` | Already in the DB. Treat as success. |
| 102 | `Message older than the stored one` | A newer version exists. Treat as success. |
| 103 | `Duplicate event request` | Same event seen in the last ~300 s, e.g. from another tool. Treat as success. |
| 104 | `Crew session` | Commander is crew, not captain, so nothing is logged. Treat as success. |
| 201 | `Missing commander name` | Fatal. Fix configuration. |
| 202 | `Missing API key` | Fatal. |
| 203 | `Commander name/API Key not found` | Fatal. Bad credentials; prompt the user. |
| 204 | `Software/Software version not found` | Fatal. `fromSoftware` or `fromSoftwareVersion` is missing. |
| 205 | `Blacklisted software` | Fatal. Your software or version is blocked; prompt the user to update. |
| 206 | `Cannot decode JSON` | Fatal. Malformed request JSON. |
| 207 | `Game/Build version not found` | Fatal. `fromGameVersion` or `fromGameBuild` is missing. |
| 208 | `Game/Build version too old` | Fatal. Legacy game data is not accepted. |
| 301 | `Message not found` | Per-event: the message was missing. |
| 302 | `Cannot decode message JSON` | Per-event: invalid event JSON. |
| 303 | `Missing timestamp/event from message` | Per-event. |
| 304 | `Discarded event` | Per-event: the event is on the discard list. |
| 401 | `Category unknown` | Per-event, ignorable. |
| 402 | `Item unknown` | Per-event: an alias is not yet known to EDSM. Ignorable, and may be reprocessed later. |
| 451 | `System probably non existant` | Per-event: the system probably doesn't exist or was moved. |
| 452 | `An entry for the same system already exists just before the visited date.` | Per-event: A→A duplicate (clock skew between tools). Ignorable. |
| 453 | `An entry for the same system already exists just after the visited date.` | Same as 452. |
| 500 | `Exception: %%` | Server exception. EDSM stores some messages for later re-processing ("Message needs to be checked"). |
| 501 | `%%` | Debug message. |

Interpretation used by clients:

- **EDMC (top level):**
  - `1xx` is OK.
  - `2xx` is fatal: the error is shown, but the pending batch is *kept* and re-sent with the next flush, where it usually fails again.
  - `5xx` means "not processed now but saved for later": the batch is treated as sent.
  - Per event: a non-`1xx` code is only logged.
  - For the system icon, `1xx`/`4xx` are OK and anything else is an error.
- **EDDiscovery:** marks an event as synced if per-event `msgnum` is `1xx` **or `500`**.
- **EDDI:** treats `100`–`104` as success.
- **Recommendation:**
  - Top-level `2xx`: stop sending for that commander, surface the error, and do not retry until the configuration changes.
  - Per-event `1xx/3xx/4xx/5xx`: mark as done (do not resend).
  - Transport errors and HTTP 5xx: retry the whole batch with exponential backoff (30 s, 60 s, 120 s … capped), keeping events queued on disk.

### 2.8 Rate-limit headers

- **What clients read:**
  - EDMC and EDDI both read `X-Rate-Limit-Remaining` and `X-Rate-Limit-Reset` from EDSM responses.
  - **EDMC** treats `X-Rate-Limit-Reset` as a **Unix epoch (seconds)** and sleeps until then when `Remaining == 0` (`plugins/edsm.py`, `send_to_edsm`).
  - **EDDI** treats it as **seconds until reset** and pauses when `Remaining < 5`.
  - **Which interpretation is right is [UNVERIFIED].**
- **What I observed:** none of my GET requests to `api-v1`, `api-system-v1`, `api-status-v1` or `api-journal-v1` returned these headers. They probably appear on authenticated or rate-limited endpoints only **[UNVERIFIED]**.
- **Robust handling:**
  - Read `X-Rate-Limit-Limit`/`-Remaining`/`-Reset` if present.
  - If `Reset > 1_000_000_000`, treat it as epoch; otherwise treat it as delta seconds.
  - When `Remaining <= 1`, pause until the reset time, capped at 1 h.
  - Also honour HTTP 429 and msgnum 429.
- **Documented limit:** `api-logs-v1/get-logs` allows **360 requests/hour per user** (≈1 per 10 s) and returns code **429** "Rate limit exceeded" when exceeded.

### 2.9 Events EDMC never sends to EDSM

From `plugins/edsm.py` and the discard behaviour above:

1. Every event on EDSM's live discard list, **except `Docked`**, which EDMC force-keeps.
2. **All events** when any of these holds:
   - the game is a beta;
   - the player is in multicrew as crew (`state['Role']` set);
   - the galaxy is not Live (`gameversion < 4.0.0`; the user is notified at most every 5 minutes);
   - the user disabled EDSM output;
   - there are no credentials for the commander.
3. Events removed by EDMC's remote killswitches (`plugins.edsm.journal`, `plugins.edsm.journal.event.<Event>`, `plugins.edsm.worker`, `plugin.edsm.worker.<Event>`).
4. Pending, not-yet-flushed events, which are dropped when a new `Fileheader` arrives or the game version/build changes before the flush. They are also cleared after `ShutDown`/`Commander`/`Fileheader`. After 3 failed transport attempts the batch stays pending and is retried with the next event.
5. Raw `Materials` events that occur before `LoadGame` are effectively replaced by the synthetic one.

The current discard list already contains journal events EDSM itself refuses, such as `Fileheader`, `Commander`, `Music`, `ShipyardNew`, `StoredModules`, `SupercruiseEntry`/`SupercruiseExit`, `Touchdown`/`Liftoff`, `FSSSignalDiscovered`, `ScanOrganic`, `NavRoute`, `Status`, `Market`, `Shipyard` and `Outfitting`.

## 3. Query APIs

General notes for this section:

- Coordinates are light years.
- Booleans are JSON `true`/`false`.
- Every endpoint answers GET and is also said to accept POST.
- `showId=1` also returns `id64` on most system endpoints (observed live and in EDD code).

### 3.1 Systems: `https://www.edsm.net/api-v1/...`

#### `GET /api-v1/system`

| Param | Default | Notes |
|---|---|---|
| `systemName`* | – | System name. |
| `showId` | 0 | 1 adds the EDSM `id` (and `id64`, observed). |
| `showCoordinates` | 0 | 1 adds `coords` (omitted if unknown). |
| `showPermit` | 0 | 1 adds `requirePermit` and `permitName`. |
| `showInformation` | 0 | 1 adds `information` (`[]` if none). |
| `showPrimaryStar` | 0 | 1 adds `primaryStar` (null if unknown). |
| `includeHidden` | 0 | 1 also returns hidden (typo/renamed) systems, with `hidden_at` and `mergedTo`. |
| `systemId`, `systemId64` | – | **Undocumented**; used by EDDiscovery ("verified Apr 2023") to look up by EDSM id or id64 instead of name. |

Live response (2026-10-12, Sol, all flags):

```json
{"name":"Sol","id":27,"id64":10477373803,"coords":{"x":0,"y":0,"z":0},"coordsLocked":true,
 "requirePermit":true,"permitName":"Sol",
 "information":{"allegiance":"Federation","government":"Democracy","faction":"Mother Gaia","factionState":"None",
   "population":18320926115,"security":"High","economy":"Refinery","secondEconomy":"Service","reserve":"Common"},
 "primaryStar":{"type":"G (White-Yellow) Star","name":"Sol","isScoopable":true}}
```

- An unknown system returns `[]`, an empty array rather than an object. This comes from EDDiscovery's handling of `/system` and `/bodies`; I did not test it live.
- With `showId`, the response may include `duplicates: [ids…]` (same-name systems).

#### `GET /api-v1/systems`

- **Params:**
  - `systemName`: a name prefix, **or** an array `systemName[]=A&systemName[]=B`.
  - `showId`, `showCoordinates`, `showPermit`, `showInformation`, `showPrimaryStar` and `includeHidden`, as for `/system`.
  - `startDateTime` and `endDateTime`, formatted `YYYY-MM-DD HH:MM:SS` in UTC and inclusive. The **maximum interval is 3 days**.
  - `onlyKnownCoordinates=1` and `onlyUnknownCoordinates=1`.
- **Output:** an array of system objects:

  ```json
  [ {"name":"Eol Prou RS-T d3-94","id":5553159,"mergedTo":3384966,"hidden_at":"2016-09-27 07:21:51"},
    {"name":"Sol","id":27,"coords":{"x":0,"y":0,"z":0}},
    {"name":"2MASS J00014645-2946387","id":9664483,"duplicates":[1946723],"coords":{"x":-46.5625,"y":-831.78125,"z":158.375}} ]
  ```

- EDD batches 20 names per query.

#### `GET /api-v1/sphere-systems`

- **Params:**
  - Centre: `systemName`* **or** `x`*/`y`*/`z`*.
  - `radius`: default 50, **max 100** ly.
  - `minRadius`: default 0.
  - The `show*` flags.
- **Output:** an array of `{ "distance": 99.89, "name": "...", "id": 2069591, "coords": {...} }`.
- EDD uses a 30 s timeout for this endpoint.

#### `GET /api-v1/cube-systems`

- **Params:**
  - Centre: `systemName`* **or** `x`/`y`/`z`.
  - `size`: default 100, **max 200** ly.
  - The `show*` flags.
- **Output:** an array of `{ "name", "id", "coords" }`.

#### Undocumented endpoints seen in EDDiscovery

- `GET /api-v1/hidden-systems?showId=1`
- `GET /api-v1/systems?pushed=1`
- `POST /api-v1/submit-distances` (old trilateration API)

### 3.4 Logs: `https://www.edsm.net/api-logs-v1/...`

#### `GET /api-logs-v1/get-logs`

- **Rate limit: 360 requests per hour per user.**
- **Params:**
  - `commanderName`* and `apiKey`*.
  - `systemName` (filter).
  - `startDateTime` and `endDateTime`, formatted `YYYY-MM-DD HH:MM:SS` in UTC and inclusive. The **max interval is 1 week**; if both are given, `endDateTime` anchors the window.
  - `showId`.
- **Output:**

  ```json
  { "msgnum": 100, "msg": "OK", "startDateTime": "2016-06-27 03:13:37", "endDateTime": "2016-06-20 03:13:37",
    "logs": [ { "shipId": 1, "system": "Sol", "systemId": 27, "firstDiscover": false, "date": "2016-06-23 02:13:37" } ] }
  ```

- EDD's parser also reads `systemId64` from each log entry, so it is present in real responses.
- **Codes:**

  | Code | Meaning |
  |---|---|
  | 100 | OK |
  | 201 | Missing commander name |
  | 202 | Missing API key |
  | 203 | Commander name/API Key not found |
  | 302 | System not in database |
  | 303 | System probably non existant |
  | **429** | Rate limit exceeded |

- **Paging:** to walk history, step the window back 1 week at a time using the returned `startDateTime`. EDD retries on 429.

#### `GET /api-logs-v1/get-position`

- **Params:**
  - `commanderName`*.
  - `apiKey`, which is optional. Without it, the position is returned only if the profile and logs are public.
  - `showId` and `showCoordinates`. With `showCoordinates=1`, the result is the last position *with* coordinates.
- **Output:**

  ```json
  { "msgnum": 100, "msg": "OK", "system": "Sol", "systemId": 27, "firstDiscover": false,
    "date": "2016-06-23 02:13:37", "coordinates": { "x": -9530.5, "y": -910.28125, "z": 19808.125 },
    "url": "https://www.edsm.net/en/user/profile/id/952/cmdr/Anthor" }
  ```

- `date` is returned only with an `apiKey` or when timestamps are public.

#### `GET /api-logs-v1/set-comment`, `get-comment`, `get-comments`

- **`set-comment`:** params `commanderName`*, `apiKey`*, `systemName`* (or `systemId`) and `comment`*. An empty comment deletes. EDD POSTs this form-encoded.
  - Output: `{ msgnum, msg, comment, lastUpdate }`.
  - Codes: 100, 201, 202, 203, 204 "Missing comment", 301, 302, 303, 305 "System name is too long or invalid".
- **`get-comment`:** params `commanderName`*, `apiKey`*, `systemName`* (or `systemId`).
  - Output: `{ msgnum, msg, comment, lastUpdate }`. msgnum 101 means "no private comment stored".
- **`get-comments`:** params `commanderName`*, `apiKey`*, `startDateTime` (inclusive, UTC) and `showId`.
  - Output: `{ msgnum, msg, comments: [ { system, systemId, comment, lastUpdate } ] }`.

## 5. Rust implementation checklist

1. **HTTP client:** `reqwest` with rustls, a 30 s timeout for the journal POST, 10–20 s for queries, gzip enabled, and a custom UA.
2. **Journal pipeline:**
   1. Tail the journals.
   2. Merge the companion files (`Cargo.json`, `ShipLocker.json`, `Backpack.json`).
   3. Update the game-state tracker (§2.3).
   4. Drop events when not Live, in beta, or in multicrew as crew.
   5. Drop events on the discard list (keep `Docked`).
   6. Stamp the six `_xxx` fields.
   7. Append to a **persistent on-disk queue** (SQLite) keyed by commander and gameversion/build.
3. **Sender task per commander:**
   - Form-encode `commanderName`, `apiKey`, `fromSoftware`, `fromSoftwareVersion`, `fromGameVersion`, `fromGameBuild`, and `message = serde_json::to_string(&batch)`.
   - Parse `{msgnum, msg, events}`.
   - Apply the §2.7 policy and back off on transport errors.
4. **Rate-limit middleware:** read the `X-Rate-Limit-*` headers (handle both epoch and delta) and HTTP/msgnum 429.
5. **Discard list:** fetch at startup, cache with a TTL (2–6 h), and fall back to the cached copy.
6. **Serde models:** model query responses with `#[serde(default)]` and `Option<…>` everywhere. Note that an unknown system returns `[]` rather than `{}`, so use an untagged enum or check for an empty array.
7. **Settings:** never log the `apiKey`. Store it in the OS keychain (`keyring` crate).
